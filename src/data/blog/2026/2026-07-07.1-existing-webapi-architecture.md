## Existing Architecture

### Overview

### Web Applications

The legacy-technology WebAPI is built using ASP.NET ASMX web services plus a tiny number of MVC WebForms. It's a monolithic application that handles all the business logic, data access, and API endpoints in a single codebase.

- .NET Full Framework 4.8
- ASP.NET ASMX Web Services
- ASP.NET MVC WebForms (tiny number of pages)
- No automated tests
- Jenkins for very basic deployment
- Hosted on AWS EC2 instances (Windows Server) with IIS

As mentioned in the previous post, there are two separate WebAPI projects that share the same database. They are both built using the same technologies and have a very similar architecture. The main difference is that they serve different business domains - one is for sales and the other is for servicing of vehicles.

### Database

The application uses a shared Microsoft SQL Server database that has been around since 2006. The database contains a large number of tables and stored procedures. Each application has it's own database (on the same server).Backup data size is about 1.5GB and 17GB respectively.

Data _access_ in the application is ADO.NET. Yeah, legacy data access code. Which _mainly_ just calls store procedures .... which means ... the business logic is mainly in the stored procedures. Which means ... the database is a huge part of the application and any migration strategy will have to take that into account.

I also want to vomit at this point. But alas, I must deal with it 😎.

## PDF Reporting

Part of the applications required PDF reports of business data - sales reports, stock and inventory numbers, etc. These reports are generated using Microsoft SQL Server Reporting Services (SSRS). The reports are designed and maintained in SSRS and are accessed via the WebAPI. The WebAPI calls the SSRS web service to generate the reports and then returns the PDF to the client.

More vomiting ensues.

## Challenges with Existing Architecture

- .NET Full Framework - old, slow, not supported anymore\*\*. Nightmare to work with _compared to modern .NET Core or even other languages like Go_.
- Microsoft Sql Server Reporting Services (wait, what?!)
- EC2 Servers - hold on, _I_ have to deal with Windows Updates?
- IIS. kill me now.
- Windows OS. I'm happy to use Win11 for development and gaming .. but not for production servers. Containers / App Service (if Azure), etc.
- Jenkins. Okay debateable, but I prefer GitHub Actions or Azure DevOps Pipelines .. these are so much easier to work with.

## AWS vs Azure

I've always struggled with AWS. Yes, I started out with "click ops" but I'm fine doing CLI. Ive just always found AWS not polished enough
and it's way more low level. **I understand that's the beauty of AWS** - you can do anything you want, but it comes at a cost of complexity.
More-so, unless you're making a high volumne application that needs low level tweaking nobs, I've found AWS to be a bit more ... messy to work with.

Over on Azure, there's a number of little things I also find frustrating but generally find the experience more conforting. Easier to use.

Both cloud providers struggle with exposing Costing and Billing. Initially I _hated_ AWS Cost Explorer. Sure, in time I figured out how to use it and other services
to find costing info. But again -> it became a lot of work to get the info. While over in Azure land it was easier ... or it just exploded and nothing even close to working.
AI tools have really help reduce this burden - give it readonly access to an account/subscription and it can speed up the process of finding costing info.

For most common use cases, I prefer Azure.
